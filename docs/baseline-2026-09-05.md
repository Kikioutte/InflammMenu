# Inflamm’Menu — état initial du 5 septembre 2026

Référence auditée : `6b58fdc9753f09243e7ed7a749acbf7c77834e16` sur `main`.
Cette analyse et les reproductions ont été réalisées avant modification du code applicatif. Les exemples emploient uniquement des données fictives.

## Produit et architecture

Application culinaire française, sans compte ni serveur de données utilisateur. Le profil, les semaines, les favoris, les notes et les recettes personnelles restent dans le navigateur. React 19, TypeScript strict, Vite 8, composants Radix et runtime mobile existant. Aucune réécriture de stack n'est justifiée.

| Couche | Responsabilité |
| --- | --- |

| `src/engine.ts` (1 908 lignes) | Génération déterministe, contraintes, portions, restes, calendrier, courses |

Le catalogue contient 630 recettes, dont 624 affichées après exclusion de six doublons. Les 80 recettes Creami restent consultables et exclues des menus. Les fichiers du runtime protégés par `AGENTS.md` restent hors périmètre de modification.

Fonctions préservées : onboarding, profil alimentaire, contraintes quotidiennes, génération hebdomadaire et semaine suivante, verrouillage, remplacement, déplacement, repas extérieurs, restes, suivi « cuisiné », courses et mode magasin, réserve quantitative, recettes personnelles, quatre préférences exclusives, notes, recherche/filtres/tri, historique et reprise, exports JSON/calendrier, restauration, confort de lecture, installation PWA et catalogue hors ligne.

## Parcours observés et forces

1. **Découverte → profil → génération : fonctionnel.** Le rôle du produit est expliqué, les choix alimentaires et matériels sont visibles, la semaine contient les repas attendus.
2. **Semaine → courses → mode magasin : fonctionnel.** Les actions produisent un retour visible et la liste reste liée au menu.
3. **Bibliothèque → catalogue → recherche → fiche : fonctionnel, état vide incomplet.** Chargement différé, allergènes et limites culinaires visibles ; aucun conseil présenté comme diagnostic.
4. **Édition et récupération : défauts sérieux reproduits ci-dessous.** Les suites existantes couvrent beaucoup de concurrence, de migrations et de scénarios métier, mais manquent ces cas précis.

Captures et mesures aux largeurs 320, 375, 390, 430, 768 et 1440 px : accueil, profil et catalogue. Aucun débordement horizontal permanent détecté sur ces écrans. Des captures prises en cours de transition ont été écartées et refaites après stabilisation. Les parcours clavier et agrandissement du texte sont également couverts par les tests existants. Axe ne relève aucune violation automatique sur les trois écrans testés à 390 et 1440 px ; cela ne constitue pas une certification WCAG ni un test avec lecteur d'écran.

## Performance, sécurité et limites

Build Sites initial : JS principal 1 362 352 octets (309 069 gzip mesuré avec Node), CSS 75 628 octets (14 343 gzip), validation différée 13 231 octets (4 185 gzip). Le catalogue complet est différé (~5,66 Mo bruts). Le budget existant du bundle principal est déjà presque atteint.

Premier passage Lighthouse mobile sur build Pages local : Performance **68**, Accessibilité **100**, Bonnes pratiques **100**, SEO **100** ; FCP 2,72 s, LCP 3,15 s, TBT 920 ms, CLS 0,057. Mesure de laboratoire sur conteneur partagé pendant d'autres tests, donc indicative et non assimilable à des Core Web Vitals réels. Aucun INP de terrain disponible.

Points forts sécurité : rendu React échappé, import JSON borné et validé, aucune exécution de HTML utilisateur repérée, images et sources validées, pas de compte ni token applicatif côté client, dépendances sans alerte connue, actions CI épinglées, CSP et politique de cache déjà présentes. La robustesse de ces protections repose sur des tests, pas seulement une recherche textuelle.

Le contenu nutritionnel est présenté comme estimation et information culinaire. La validation éditoriale automatisée ne remplace pas une expertise nutritionnelle recette par recette. Les allergies autres que les 14 catégories réglementaires existent : https://www.ameli.fr/assure/sante/themes/allergie-alimentaire/definition-symptomes. L'interface doit rendre explicite ce qu'elle sait exclure et ne jamais accepter silencieusement une contrainte inconnue.

À arbitrer sans changement imposé : origine/domaine de production dédié, liens profonds vers les recettes, refonte du découpage des écrans, validation nutritionnelle externe. Aucune perte de données ni changement de concept n'est acceptable pour améliorer un score.
